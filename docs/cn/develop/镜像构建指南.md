# 镜像构建指南

本文档说明 MuseFlow 各服务 Docker 镜像的构建方法、镜像清单与常见坑。
所有构建命令均在**仓库根目录**执行，构建上下文为仓库根（前端与后端一致）。

## 镜像清单

| 镜像名 | 来源 | 用途 | Dockerfile |
| --- | --- | --- | --- |
| `museflow/user-service` | `services/user-service`（`cmd/server`） | gRPC 用户服务（:5002） | `services/user-service/Dockerfile` |
| `museflow/user-service-worker` | `services/user-service`（`cmd/worker`） | asynq 消费端，负责邮件发送等慢速任务 | `services/user-service/Dockerfile`（`--target worker`） |
| `museflow/api-gateway` | `services/api-gateway`（`cmd/server`） | HTTP 网关（:5001） | `services/api-gateway/Dockerfile` |
| `museflow/config-service` | `services/config-service`（`cmd/server`） | gRPC 系统配置服务（:5004） | `services/config-service/Dockerfile` |
| `museflow/web` | `web/`（Vue 3 SPA） | 前端静态站点（Nginx 托管） | `deploy/k8s/applications/web/frontend/Dockerfile` |

> 邮箱发送**不是独立服务**，而是 user-service 的 `cmd/worker`（asynq 消费端），
> 以独立镜像 `museflow/user-service-worker` 部署。

## 创建镜像

```bash
# user-service（gRPC 服务端，默认 target）
docker build -f services/user-service/Dockerfile -t museflow/user-service .

# user-service worker（asynq 消费端）
docker build -f services/user-service/Dockerfile --target worker -t museflow/user-service-worker .

# api-gateway
docker build -f services/api-gateway/Dockerfile -t museflow/api-gateway .

# config-service（gRPC 系统配置服务）
docker build -f services/config-service/Dockerfile -t museflow/config-service .

# web（前端 SPA）
docker build -f deploy/k8s/applications/web/frontend/Dockerfile -t museflow/web .
```

## 验证镜像

```bash
# 查看本地镜像与大小
docker images museflow

# 冒烟：启动含 Nginx 签名与版本信息（不依赖 DB/Redis 的静态服务）
docker run --rm -p 8080:80 museflow/web
```

## 导出镜像

```bash
# 导出镜像到 tar 文件
docker save -o museflow-images.tar museflow/api-gateway:latest museflow/user-service-worker:latest museflow/user-service:latest museflow/config-service:latest museflow/web:latest
```

> 文档不写具体主机地址；本机验证一律使用 `localhost` 回环地址。

## 更新与清理

```bash
# 删除构建缓存（调整基础镜像或依赖后避免误用旧层）
docker builder prune

# 删除不再使用的镜像
docker rmi museflow/web
```

## 常见坑与约定

### go.mod 本地 replace 模块必须复制进构建上下文

`user-service`、`api-gateway`、`config-service` 的 `go.mod` 通过 `replace` 指向本仓库 `pkg/` 下的共享模块
（`pkg/envloader`、`pkg/logger`、`pkg/errcode`）。关键点：

- Dockerfile 必须先复制被 replace 模块的 `go.mod`/`go.sum`，`go mod download` 才能解析模块图；
- 复制源码阶段也要整体复制 `pkg/`，否则编译报“package not found”。

`config-service` 与 `api-gateway` 还 `replace github.com/museflow/proto => ../../proto`，
共享 gRPC 契约（`proto/model.proto` 即由 config-service 提供实现），
因此其 Dockerfile 需额外 `COPY proto/go.mod proto/go.sum` 并整体复制 `proto/`。

### go.work 会掩盖 go.mod 不完整

本地开发由 `go.work` 解析模块图，各服务 `go.mod` 的缺漏在本地不可见。
推荐在**无工作区环境**校验单模块自足：

```bash
# 在对应服务目录执行（先设置 GOWORK=off）
$env:GOWORK='off'
go mod tidy
go build ./cmd/server
# 构建通过后恢复：Remove-Item Env:GOWORK
```

go.mod 以无工作区环境（即 Docker 构建）为准。

### user-service 双 target：默认构建产物是 server

`user-service/Dockerfile` 用 BuildKit 多 target 产出 server 与 worker 两个镜像。
`docker build` 不带 `--target` 时默认构建**最后一个 stage**，因此 server 阶段必须保持在文件末尾，
避免默认产物漂移为 worker；worker 必须显式使用 `--target worker`。

### 前端基础镜像使用跟随型 tag

`web` Dockerfile 使用 `node:lts-alpine` 与 `nginx:stable-alpine`，跟随官方 LTS/稳定分支。
首次构建前需确保能拉取基础镜像；若网络受限可先手动拉取：

```bash
docker pull node:lts-alpine
docker pull nginx:stable-alpine
```

### 构建上下文精简

仓库根 `.dockerignore` 排除 `node_modules`、`.venv`、`dist`、`.git` 等，
避免把数百 MB 的依赖与产物打进构建上下文。增删 Dockerfile 的 `COPY` 源时需复核是否被忽略。
