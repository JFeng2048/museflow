# 模型与系统配置设计

**一句话概括**：配置管理域独立成 `config-service`（gRPC，`:5004`），用 `config_svc` 五张表分别承载「平台渠道与模型」「用户自定义渠道与模型」「通用系统配置」，密钥 AES-256-GCM 加密后只写不读，前端经 api-gateway 消费。

## 背景与边界

模型配置要回答三个问题：平台提供哪些模型、用户自带哪些模型、系统里还有哪些可调参数。这与用户账号域的关注点不同——账号域关心「谁登录了、有什么权限」，配置域关心「有哪些上游、凭据是什么、调用参数怎么配」。混在一个服务里会让用户域背上上游协议知识，也会让平台密钥与账号数据共享同一套备份与审计边界，因此单独拆出配置域。

| 数据 | 谁维护 | 落在哪 | 消费方 |
| :--- | :--- | :--- | :--- |
| 平台渠道（厂商 + `base_url` + `api_key`） | 管理端 | `config_svc.model_provider` | 平台侧，用户端不可见 |
| 平台模型明细 | 管理端 | `config_svc.model` | 用户端「刷出来」的可用模型 |
| 用户自定义渠道 | 用户本人 | `config_svc.user_model_provider` | 仅本人 |
| 用户自选模型 | 用户本人 | `config_svc.user_model` | 仅本人 |
| 通用系统配置 | 管理端 | `config_svc.system_setting` | 后台；标 `is_public` 的下发前端 |

两张用户表没有放在 `user_svc`，而是与平台表同处 `config_svc`：模型配置是一个内聚主题，五张表共用 `model_type` / `protocol` / `capabilities` 同一套枚举与校验，放在一起不必跨 schema 复制约束。归属用 `user_uuid` 逻辑关联、不建物理外键，后续真要拆库时，把带 `user_uuid` 的两张表迁走即可。归属校验一律在 service 层按 `user_uuid` 收敛，因此改不到别人的渠道。

职责边界：本服务只做「模型目录 + 凭证 + 系统配置」的读写与加解密，不调用上游大模型。将来生成服务要模型时，作为 gRPC 客户端来取配置，HTTP 请求由它自己发。

## 数据表设计

DDL 见 `services/config-service/database/config_svc.sql`，与 `user_svc.sql` 同一套约定：int8 自增主键 + 每表独立序列、`updated_at` 由 BEFORE UPDATE 触发器维护、全字段中文 COMMENT、序列按 `max(id)+1` 对齐。这是 `DROP + CREATE` 全量脚本，只用于空库初始化。

| 表 | 作用 | 关键字段 | 唯一约束 |
| :--- | :--- | :--- | :--- |
| `model_provider` | 平台渠道：厂商 + `base_url` + 加密后的 `api_key` | `code`、`protocol`、`api_key_hint`、`is_active` | `code` |
| `model` | 平台模型明细，挂在平台渠道下 | `provider_id`、`model_type`、`api_model`、`context_window`、`credit_cost` | `code`、`(provider_id, api_model)` |
| `user_model_provider` | 用户自定义渠道，凭据由用户本人填写 | `user_uuid`、`protocol`、`api_key_hint` | `(user_uuid, name)` |
| `user_model` | 用户自选模型，只能挂在自己的渠道下 | `user_uuid`、`user_provider_id`、`model_type`、`api_model` | `(user_uuid, user_provider_id, api_model)` |
| `system_setting` | 通用系统配置，key-value + jsonb | `config_group`、`key`、`value` / `secret_value`、`is_public` | `(config_group, key)` |

枚举取值：

| 字段 | 取值 |
| :--- | :--- |
| `model_type` | `chat` 对话大模型 / `embedding` 向量化 / `rerank` 重排序 / `vision` 视觉理解 / `image` 图像生成 / `audio` 语音 / `video` 视频 |
| `protocol` | `openai`（OpenAI 兼容）/ `anthropic` / `gemini` / `custom` |
| `value_type` | `string` / `number` / `bool` / `json`，只用于后台表单渲染 |

三点设计取舍：

1. **平台模型与用户模型分成两张表**，不合并成一张加 `owner` 字段。平台模型有 `code` 与 `credit_cost`（平台计费），用户模型两者都没有（用户直接向上游付费，约定对平台免费）；字段差异本身就在说明它们不是一回事。
2. **`code` 与 `api_model` 分开**：`code` 是平台内部引用的稳定标识，`api_model` 是真正传给上游的模型名，两者常常不同（内部叫 `muse-pro`，上游叫 `gpt-4o`）。
3. **`system_setting` 用 jsonb 存值**，同时用两条 CHECK 约束把「非机密值 `value`」与「机密值 `secret_value`」约束成恰好一个非空，且 `is_secret` 与 `secret_value` 是否非空一致，从数据库层面杜绝同一份配置存两处。

## 密钥处理

`model_provider.api_key`、`user_model_provider.api_key`、`system_setting.secret_value` 三处一律密文落库，由 `internal/pkg/secret` 做 AES-256-GCM 加密，格式 `v1:<nonce_b64>:<ciphertext_b64>`，`v1:` 前缀留给将来轮换算法时识别旧数据。

- 主密钥取共享环境变量 `MODEL_SECRET_KEY`（无前缀，与 `JWT_SECRET` / `DB_*` 同级），长度必须 32 字节，启动时强校验、不做长度自适应：哈希派生会把「密钥配错」变成「静默得到另一把可用密钥」，轮换后的密文解不开反而更难排查。
- 读取侧不回明文：任何响应里只有 `api_key_hint`（末 4 位）与 `api_key_updated_at`。`base_url` 对管理端可见（排查连通性要用），`api_key` 明文任何接口都不返回。
- **唯一的解密路径是上游模型目录探测**（`internal/service/remote.go`）。只有「拉一次厂商有哪些模型」需要拿到明文密钥，其余场景一律用不到，解密出口因此只有这一处。
- 解不开（密钥已轮换、密文损坏）时返回 `ErrCredentialUnreadable`，映射为 gRPC `FailedPrecondition`：重试同一个请求没有意义，文案本身就是给用户的下一步提示「重新填写密钥」。

## 分层与模块

沿用仓库既有约束 `handler → service → repository` 单向依赖，对应 `services/config-service/internal/`：

| 目录 | 职责 |
| :--- | :--- |
| `handler` | gRPC handler，proto ↔ service 转换，`mapError` 把业务错误映射为 gRPC status |
| `service` | 业务逻辑，按表拆文件（`provider` / `model` / `user_*` / `setting` / `available` / `remote`） |
| `repository` | GORM 数据访问，唯一约束冲突按约束名分流文案 |
| `model` | GORM 实体，`TableName()` 固定 `config_svc.*` |
| `pkg/secret` | AES-256-GCM 加解密，只在写入侧加密 |
| `pkg/upstream` | 上游 `/models` 目录客户端，本服务唯一出网的路径 |

service 没有像 user-service 那样拆 `auth` / `token` 子包：「用户端可用模型」要合并平台模型与用户自定义模型，五张表共用一个 `Service` 才能顺理成章地做这种跨表视图，拆子包只会让仓储在包间来回传递。

配置分层遵循 `AGENTS.md`：服务键用 `CONFIG_` 前缀（`env.Get`），共享键无前缀（`MODEL_SECRET_KEY`、`DB_*`，`env.GetCommon`）。

## 上游模型目录探测

管理员在后台填完 `base_url` 与密钥后，先当场探测能不能连通、有哪些模型，再决定要不要落库，省去手抄 `api_model`。凭证有三种定位方式，按优先级取第一个非空的：

| 定位方式 | 使用方 | 密钥来源 |
| :--- | :--- | :--- |
| `provider_id` | 管理端平台渠道 | 读库解密，请求与响应都不携带明文 |
| `user_provider_id` + `user_uuid` | 用户端我的渠道 | 读库解密，带归属校验，取不到别人的渠道 |
| `base_url` + `api_key` | 两边都能用 | 请求体里的临时凭证，渠道还没保存时的探测 |

探测限制：超时 15s、响应体上限 4MB、返回条目上限 500 条（厂商目录动辄上千条，而后台只需要勾选常用的那一批）。停用中的平台渠道同样允许探测——停用只是不再对用户端可见，后台维护时仍需核对模型清单。探测只读上游、不写库。

## 系统配置语义

| 字段 | 语义 |
| :--- | :--- |
| `is_secret` | 是否为机密配置，与 `secret_value` 是否非空由 CHECK 约束锁死一致 |
| `is_public` | 是否可下发前端，只有标 `true` 的才随 `/user/settings` 返回 |
| `value_type` | 后台表单渲染提示，落库不做强制校验 |

接口分层：`/admin/settings/*` 全量读写（管理端），`/user/settings` 只读且只回 `is_public=true` 的项。机密值的明文只在写入响应里回显一次，之后任何读取路径都拿不到。

jsonb 存的字符串值回来是带引号的 JSON 文本（`"MuseFlow"`），由前端 `decodeSettingValue` 解一层，视图层不感知这层编码。

## 前端

三个入口，路由权限均为 `system:admin` 或登录态：

| 路由 | 视图 | 内容 |
| :--- | :--- | :--- |
| `/admin/models` | `web/src/views/admin/Models.vue` | 平台渠道 + 平台模型 |
| `/admin/settings` | `web/src/views/admin/Settings.vue` | 系统配置 |
| `/settings`「模型配置」标签 | `web/src/views/settings/ModelSettings.vue` | 可用模型 / 平台公开配置 / 我的渠道 / 我的模型 |

代码组织：

- API 层 `web/src/api/model/index.ts`，与视图解耦，`snake_case` → `camelCase` 转换都在这一层。
- 状态层 `web/src/stores/model.ts`，跨页面共享渠道与模型状态。
- 类型分两层：`web/src/types/model/dto.ts` 对齐后端 DTO，`web/src/types/model/index.ts` 是前端领域模型。
- 复用组件集中在 `web/src/components/model/`：`ProviderFormModal`、`ModelFormModal`、`SettingFormModal` 三个表单弹窗，加 `KeySlot`（密钥脱敏展示与轮换）与 `CapabilityIcons`（能力开关图标）。
- 样式单独放 `web/src/assets/styles/components/_model.css`，只服务模型配置相关页面，不往全局样式里掺。
- Mock 已清理：`web/src/mock/models.ts` 删除，模型与系统配置全部走真实接口。

## 部署

- 服务端口 `5004`（`5003` 已被 crawl4ai-service 占用），网关侧对应 `GATEWAY_MODEL_SERVICE_URL`。
- Chart 在 `deploy/k8s/applications/services/config-service/`，接入 `deploy/k8s/scripts/` 的部署脚本与推送流程。
- `MODEL_SECRET_KEY` 与 `JWT_SECRET` 同级，集中放在 `deploy/k8s/applications/overlays/secrets.yaml`，不入库；一旦变更，历史密文全部无法解密。
- HTTP 契约文档：api-gateway 的 Swagger（`/swagger/index.html`），标签 `model-模型与系统配置`。
