# 双令牌认证系统设计文档

## 概述

双令牌机制，实现完整的用户认证系统。

当前实现载体为 Go 微服务：

| 组件 | 职责 |
|------|------|
| `services/api-gateway` | 对外暴露 HTTP 接口（Gin），管理 Cookie，转发 gRPC |
| `services/user-service` | 认证业务逻辑、令牌签发与吊销、用户数据访问 |
| `proto/user/user.proto` | 两者之间的 gRPC 契约 |
| PostgreSQL `user_svc` schema | 用户主表等持久化数据（见 `services/user-service/database/user_svc.sql`） |
| Redis | refresh token 白名单、access token 黑名单、设备会话列表 |

### 核心设计

- **双令牌**：access token（短期 1h，无状态 JWT，放响应 body）+ refresh token（长期 30d，JWT + Cache 白名单，放 HttpOnly Cookie）
- **刷新不轮换**：同一个 refresh token 在有效期内可反复换新 access token
- **refresh 白名单删除策略**：吊销即删除 Cache 中的 valid 标记，省内存
- **access 黑名单**：登出时将 access token 的 `jti` 写入黑名单，TTL 取其**剩余有效期**，到期由 Redis 自动清理。这样登出后未过期的 access token 也会立即失效
- **设备指纹**：`sha256(deviceId + User-Agent + IP)`，防止 refresh token 被窃取后跨设备使用
- **密码加密**：bcrypt（cost 可配，默认 10；密码长度上限 72 字节）
- **登录账号**：email（`user_svc.users.email` 唯一且非空）

> 为什么 refresh 用白名单而 access 用黑名单：
> refresh token 数量少、生命周期长，白名单便于设备管理与主动吊销；
> access token 数量多、生命周期短，仅在"登出后剩余有效期"这段窗口内需要拦截，
> 黑名单条目会随 TTL 自动消失，内存开销可控。

## 令牌机制

### Access Token

| 属性 | 值 |
|------|---|
| 格式 | JWT（HS256 签名） |
| 有效期 | 1 小时（`ACCESS_TTL_SECONDS=3600`） |
| 存储 | 响应 body → 前端内存（防 XSS） |
| 传输 | `Authorization: Bearer <token>` |
| 验证方式 | JWT 验签 + type 检查 + 过期检查 + **Redis 黑名单检查** |
| payload | `{sub, jti, type:"access", iat, exp}` |

`sub` 为用户 `uuid`（对外标识，不使用自增 id）；`jti` 为该 token 的唯一 ID，登出时用作黑名单键。

### Refresh Token

| 属性 | 值 |
|------|---|
| 格式 | JWT（HS256 签名） |
| 有效期 | 30 天（`REFRESH_TTL_SECONDS=2592000`） |
| 存储 | HttpOnly Cookie（JS 读不到，防 XSS） |
| 传输 | Cookie 自动携带 |
| 验证方式 | JWT 验签 + 设备校验 + Cache 白名单检查 |
| payload | `{sub, type:"refresh", tokenId, deviceId, deviceFingerprint, iat, exp}` |

### Cookie 属性

| 属性 | 值 |
|------|---|
| `HttpOnly` | True（refresh token），False（device id） |
| `SameSite` | lax（可配置：lax / strict / none） |
| `Secure` | 生产环境开启（`COOKIE_SECURE=true`，仅 HTTPS） |
| `Path` | / |
| `Max-Age` | 30 天 |

> 因需携带 Cookie，CORS 的 `Access-Control-Allow-Origin` 不能为 `*`，
> 必须按 `ALLOW_ORIGINS` 白名单回显具体来源并设置 `Allow-Credentials: true`。

## Cache 数据结构

### 1. refresh token 有效性白名单

```
键: auth:refresh:valid:{tokenId}
值: "active"
TTL: 30天
```

存在即有效，删除即失效（白名单删除策略）。

### 2. access token 黑名单

```
键: auth:access:blacklist:{jti}
值: "revoked"
TTL: 该 access token 的剩余有效期（<=1h）
```

存在即已吊销。TTL 到期自动清理，无需额外的清理任务。
若登出时 access token 已过期，则跳过写入。

### 3. 用户 token 元数据列表

```
键: auth:user:tokens:{userId}
值: JSON数组
TTL: 30天
```

```json
[
  {
    "tokenId": "uuid",
    "deviceId": "device-uuid",
    "deviceName": "Chrome on Windows",
    "loginTime": "2026-08-27T12:00:00+08:00",
    "lastRefreshTime": "2026-08-27T12:30:00+08:00"
  }
]
```

用于设备列表展示和批量吊销。

## 完整流程

### 1. 注册（`POST /api/v1/auth/register`）

```
请求: email + password + nickname(可选)
  │
  ├─ 参数校验（email 格式、password 8-72 字节）
  ├─ 邮箱规范化（trim + 转小写）
  ├─ 唯一性校验（email）
  ├─ nickname 兜底（为空时取邮箱前缀，因 users.nickname 为 NOT NULL）
  ├─ bcrypt 哈希密码（cost=10）
  └─ 写入 user_svc.users（uuid 由服务端生成）

响应: {code, message, data: UserInfo}
```

### 2. 登录（`POST /api/v1/auth/login`）

```
请求: email + password + device_name(可选)，Cookie 中可带已有 device_id
  │
  ├─ 按 email 查询用户
  ├─ bcrypt 密码校验
  │   用户不存在与密码错误返回同一错误，避免邮箱枚举
  ├─ 生成 tokenId = uuid4()，deviceId 缺失时由服务端生成
  ├─ 计算 deviceFingerprint = sha256(deviceId + UA + IP)
  ├─ 签发 access token（JWT，1h，含 jti）
  ├─ 签发 refresh token（JWT，30d，含 deviceId + deviceFingerprint）
  ├─ Redis 写入白名单: auth:refresh:valid:{tokenId} = "active" (TTL=30d)
  ├─ Redis 写入用户 token 列表
  ├─ 更新 users.last_login_at / last_login_ip（失败仅告警，不阻断登录）
  ├─ access token → 响应 body
  ├─ refresh token → HttpOnly Cookie
  └─ device_id → 普通 Cookie

响应: {access_token, token_type, expires_in, user} + Set-Cookie: refresh_token, device_id
```

> 说明：`login_fail_count` / `locked_until` / `status` 字段已在数据模型中保留，
> 但当前登录流程不做失败计数、锁定与状态阻断，留待后续迭代。

### 3. 刷新（`POST /api/v1/auth/refresh`）

```
请求: 无 body（从 Cookie 读取）
  │
  ├─ 从 Cookie 读 refresh_token + device_id
  ├─ 缺任一 → 401
  │
  ├─ 步骤1: JWT 解码 + 验签（限定 HS256）
  │   失败 → 401 "刷新令牌无效"
  │
  ├─ 步骤2: 令牌类型检查
  │   payload.type == "refresh" ?
  │   否 → 401（防止 access token 被当作 refresh 使用）
  │
  ├─ 步骤3: 提取 tokenId + sub
  │   缺失 → 401 "缺少 tokenId 或 sub 声明"
  │
  ├─ 步骤4: deviceId 比对
  │   JWT内的 deviceId == Cookie的 device_id ?
  │   否 → 403 "设备校验失败"
  │
  ├─ 步骤5: 设备指纹比对
  │   重新计算 sha256(device_id + User-Agent + IP)
  │   与 JWT 内的 deviceFingerprint 比对
  │   不一致 → 403 "设备校验失败"
  │
  ├─ 步骤6: Redis 白名单检查
  │   EXISTS auth:refresh:valid:{tokenId} ?
  │   不存在 → 401 "令牌无效或已失效"
  │
  ├─ 签发新 access token（refresh 不变，不轮换）
  └─ 更新 Redis 中 token 的 lastRefreshTime

响应: {access_token, token_type, expires_in}
失败为 401 时，网关会清除 Cookie，避免客户端反复重试
```

### 4. 登出（`POST /api/v1/auth/logout`）

```
请求: 需 access token（Authorization 头），Cookie 带 refresh_token
  │
  ├─ 处理 refresh token（存在时）
  │   ├─ 解码取 tokenId
  │   ├─ 删除白名单: DEL auth:refresh:valid:{tokenId}
  │   └─ 从用户 token 列表移除该 tokenId
  │
  ├─ 处理 access token（存在且未过期时）
  │   ├─ 解码取 jti 与 exp
  │   ├─ ttl = exp - now
  │   └─ 写入黑名单: SET auth:access:blacklist:{jti} "revoked" EX ttl
  │
  └─ 清除两个 Cookie（refresh_token + device_id）

响应: {code, message}
```

两个令牌各自尽力处理：任一解析失败不影响另一个的吊销，
保证客户端只带其中一个时也能完成登出。

## 认证中间件

`api-gateway/internal/middleware/auth.go` 中的 `Auth`：

1. 从 `Authorization: Bearer <token>` 提取 access token，缺失 → 401
2. 调用 user-service 的 `ValidateToken`（含验签、类型、过期、**黑名单**检查）
3. 校验通过后将用户 `uuid` 写入 `gin.Context`，下游用 `middleware.CurrentUserUUID(c)` 获取

> 网关不在本地验签，而是回调 user-service：
> 因为黑名单状态存于 user-service 侧的 Redis，
> 仅本地验签无法感知令牌已被登出吊销。

## 配置说明

### api-gateway

| 环境变量 | 默认值 | 说明 |
|------|--------|------|
| `PORT` | 5001 | HTTP 监听端口 |
| `USER_SERVICE_URL` | localhost:5002 | user-service gRPC 地址 |
| `JWT_SECRET` | (必填) | JWT 签名密钥，需与 user-service 一致 |
| `ALLOW_ORIGINS` | http://localhost:5173 | CORS 白名单，逗号分隔 |
| `COOKIE_SECURE` | false | 生产环境（HTTPS）置 true |
| `COOKIE_SAMESITE` | lax | Cookie SameSite 策略 |
| `COOKIE_DOMAIN` | (空) | Cookie 作用域 |

### user-service

| 环境变量 | 默认值 | 说明 |
|------|--------|------|
| `PORT` | 5002 | gRPC 监听端口 |
| `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` | 见 `.env.example` | 数据库连接配置（所有服务共用的公共配置，由系统拼装为 DSN） |
| `JWT_SECRET` | (必填) | JWT 签名密钥（gateway 与 user-service 共享，用于双方验签） |
| `REDIS_ADDR` | localhost:6379 | Redis 地址 |
| `REDIS_PASSWORD` | (空) | Redis 密码 |
| `REDIS_DB` | 0 | Redis 库号 |
| `ACCESS_TTL_SECONDS` | 3600 | access token 有效期 |
| `REFRESH_TTL_SECONDS` | 2592000 | refresh token 有效期 |
| `BCRYPT_COST` | 10 | bcrypt 加密成本 |

## API 端点汇总

| 方法 | 路径 | 鉴权 | 功能 |
|------|------|------|------|
| POST | `/api/v1/auth/register` | 无 | 用户注册（email） |
| POST | `/api/v1/auth/login` | 无 | 登录（email + password） |
| POST | `/api/v1/auth/refresh` | 无（走 Cookie） | 刷新 access token |
| POST | `/api/v1/auth/logout` | 需要 access | 登出（吊销当前设备） |
| GET | `/api/v1/user/profile` | 需要 access | 获取当前用户信息 |
| GET | `/health` | 无 | 健康检查 |
| GET | `/swagger/index.html` | 无 | Swagger 文档 |
