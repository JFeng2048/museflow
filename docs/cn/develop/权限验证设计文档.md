# 权限验证设计文档

## 概述

user-service 采用轻量级 RBAC：内置三个角色，权限由业务代码集中校验，无独立权限管理界面。

## 角色模型

系统仅内置三个角色，不可被业务代码删除或改名：

| 角色 key | 说明 |
|----------|------|
| `super_admin` | 超级管理员，拥有全部权限 |
| `admin` | 管理员，拥有除角色管理外的运营权限 |
| `user` | 默认用户，仅自身资源相关权限 |

角色与权限的映射关系在 `internal/service/rbac` 中以代码常量定义，
不通过数据库 seed 写入（避免与运行期数据耦合）。

## 权限校验方式

权限校验不依赖「角色→权限」的运行时查询，而是直接由业务代码完成：

1. 接口层声明所需权限码（如 `user:read`、`role:manage`）。
2. 网关从 access token 中解析出 `user_id`（即 `user_uuid`）。
3. 调用方传入待操作资源的 `user_id`，服务端将其与 token 中的 `user_id` 比对：
   - 一致 → 本人操作，放行；
   - 不一致 → 校验调用者是否持有对应管理权限码（如 `user:manage`），
     持有则放行，否则返回 403。

这种「本人比对 + 权限码」的两段式校验，既覆盖普通用户自助场景，
也覆盖管理员代操作场景，且无需每次查询角色树。

## 权限缓存

权限判定结果（用户是否持有某权限码）通过 Redis 缓存：

- key：`perm:user:{uuid}`
- TTL：7 天
- 角色/权限变更时主动清除该 key，保证最终一致。

## 审计

所有敏感操作（角色变更、权限校验失败、2FA 事件等）写入 `user_svc.audit_log`，
记录操作人、动作、目标与 IP，供安全追溯。
