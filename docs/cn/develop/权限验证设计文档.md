# 权限验证设计文档

## 概述

user-service 采用轻量 RBAC：三个系统角色 + 权限码，分两条设计线：

- **数据**：角色、权限定义、角色-权限映射都落在数据库，服务启动时由 `internal/bootstrap`
  播种保证存在（缺什么补什么），管理员可在后台调整映射。
- **校验**：网关按路由声明所需权限码，调用 user-service 的 `CheckPermission`；
  其中 `super_admin` 走通配，不参与逐条校验。

权限数据不再写死在代码常量里，因此**空库也能直接启动**并自愈出可用的 RBAC 数据。

## 角色模型

| 角色 code | 名称 | 默认权限 | 是否可调整 |
|---|---|---|---|
| `super_admin` | 超级管理员 | 全部权限（通配，不依赖映射） | 映射可在后台改，但校验不看它 |
| `admin` | 管理员 | 默认无权限（与 SQL 种子一致） | 是，在后台「角色权限」里勾选 |
| `user` | 普通用户（注册与第三方登录自动授予） | 8 条创作相关权限 | 是 |

`admin` 默认为空是种子数据的原样：需要哪些运营权限由部署方在后台决定，代码不擅自扩大。

## 权限码

权限定义表 `user_svc.permission` 共 17 条（启动播种按 `code` 幂等补齐）：

| 资源 | 权限码 |
|---|---|
| `user` | `user:read` / `user:write` / `user:delete` / `user:admin` |
| `novel` | `novel:read` / `novel:write` / `novel:delete` / `novel:publish` / `novel:admin` |
| `material` | `material:read` / `material:write` |
| `publish` | `publish:read` / `publish:write` / `publish:admin` |
| `system` | `system:admin` |
| `hotspot` | `hotspot:read` / `hotspot:write` |

`user` 角色的默认权限共 8 条：`novel:read`、`novel:write`、`novel:publish`、
`material:read`、`material:write`、`publish:read`、`publish:write`、`hotspot:read`。

## 启动播种（internal/bootstrap）

`cmd/server` 启动时执行一次，全程幂等：

| 播种内容 | 规则 |
|---|---|
| 系统角色 | 三个角色缺失即创建（`role.id` 未绑定序列，按 `max(id)+1` 赋值） |
| 权限定义 | 按 `code` 补齐缺失项，已存在的跳过 |
| 角色默认权限 | **仅当该角色当前没有任何权限时**写入默认映射 |
| 管理员账号 | 按 `USER_ADMIN_EMAIL` 查库，不存在则创建并授予 `super_admin` |

不覆盖原则（避免重启改坏线上状态）：

- 已存在账号的密码不变；忘记密码用 `USER_ADMIN_RESET_PASSWORD=true` 重启一次重置；
- 后台调整过的角色权限不变（只在角色权限为空时才写默认值）；
- 账号已有 `super_admin` 角色时不重复授予。

配置项：

| 变量 | 默认 | 说明 |
|---|---|---|
| `USER_ADMIN_EMAIL` | 空 | 管理员邮箱；留空则跳过管理员播种 |
| `USER_ADMIN_PASSWORD` | 空 | 初始密码，仅账号不存在（或打开重置开关）时使用 |
| `USER_ADMIN_NICKNAME` | `系统管理员` | 昵称 |
| `USER_ADMIN_RESET_PASSWORD` | `false` | 应急开关：重启一次即把密码重置为上面的值 |

失败处理：播种失败只记 ERROR 日志、不阻断启动（已有账号仍可登录），避免配置遗漏导致
Pod 反复重启；日志里会明确指出是哪一步失败。

与 `database/user_svc.sql` 的关系：

- 代码播种与 SQL 导出的内容一一对应（含权限顺序，因此全新库上生成的 id 也一致）；
- 代码播种负责「让服务在任何情况下都能启动」，包括被清空的库；
- SQL 文件是全量导出，用于对照与手工重建，部署时**不需要**执行（它是 `DROP` + `CREATE`，
  重跑会清空数据）。

## super_admin 通配

`super_admin` 不逐条授予权限：

- 计算权限时（`resolvePermissions`）发现该角色，缓存里只写通配标记 `*`；
- `CheckPermission` 命中标记直接放行——权限表里尚未出现的权限码也通过；
- 对外查询权限列表（`/user/permissions`）时展开为权限表中的全部编码，前端菜单/按钮无需特殊处理。

这样做的原因：

1. 新增权限码时不必再给系统管理员补授权；
2. 逐条展开会引入「缓存里缺新权限」的窗口期（缓存 TTL 与 refresh token 一致，默认 30 天），通配不存在这个问题。

`super_admin` 的角色-权限映射仍然写入数据库，用于后台界面展示与 SQL 导出对齐，**校验不依赖它**。

## 权限校验链路

1. 网关路由声明所需权限码：管理后台 `/api/v1/admin/**` 统一要求 `user:admin`
   （见 `services/api-gateway/internal/router/v1/admin_router.go`）。
2. `middleware.RequirePermission` 用 access token 中的 `user_uuid` 调 user-service 的 `CheckPermission`。
3. user-service 的 `rbac.Service.CheckPermission`：读缓存 `perm:user:{uuid}` → 未命中则计算
   （通配或按 `role_permission` 汇总）并回写 → 比对权限码。
4. 未持有 → 403。

服务内部另有一类「本人操作」判断（传入的 `user_id` 与 token 中的不一致时才要求管理权限码），
与上面的权限码校验互补：前者管资源归属，后者管能力边界。

## 权限缓存

- key：`perm:user:{uuid}`，value 为逗号分隔的权限码（`super_admin` 为 `*`）
- TTL：与 refresh token 一致（`USER_REFRESH_TTL_SECONDS`，默认 30 天）
- 主动失效：分配/移除角色、覆盖角色权限、删除角色时清理相关用户缓存
- 缓存不可用：降级查库并打 WARN 日志，不阻断请求

## 后台可调整的内容

- 角色权限映射：`PUT /api/v1/admin/roles/{id}/permissions`（覆盖式），变更后清理该角色下所有用户的缓存
- 角色名称与描述：`PUT /api/v1/admin/roles/{id}`；系统角色不可改 `code`、不可删除
- 新增角色：系统角色之外可自建角色并分配权限

## 排障

| 现象 | 处理 |
|---|---|
| 管理后台全部 403 | 该账号是否持有 `super_admin`（通配）或 `user:admin`；看权限缓存与 `CheckPermission` 结果 |
| 权限码少了几条 | 看启动日志「已补齐系统权限 count=N」；权限表为空时重启即自愈 |
| 清空的角色权限又回来了 | 播种只在角色权限为空时写默认值，属预期行为（见「启动播种」） |
| 注册报 `duplicate key ... "user_pkey"` | 序列与数据 `max(id)` 不同步，复位语句见 `database/user_svc.sql` 的「序列对齐」段 |
| 忘记管理员密码 | `USER_ADMIN_RESET_PASSWORD=true` 重启一次，之后改回 `false` |

## 审计

所有敏感操作（角色变更、权限校验失败、2FA 事件等）写入 `user_svc.audit_log`，
记录操作人、动作、目标与 IP，供安全追溯。
